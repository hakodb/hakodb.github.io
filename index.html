Why HakoDB

The zero-deploy footprint of an embedded engine, with the query power of a document cloud.

Fully in-process

Single-file storage, WAL + tiered segments, group-commit batching. Copy the file, ship the app.

Firestore-style queries

Filters, ordering, cursors, projections, count/sum/avg — plus composite, full-text and secondary indexes built in the background.

Zero-copy reads

Projections decode straight from memory-mapped bytes. Dotted-path pulls skip whole-subtree decode — ~18× on nested docs.

Encryption at rest

ChaCha20-Poly1305 over WAL and segments, per-collection keys — with fail-closed sync guards so encrypted rooms never leak plaintext.

Live watch streams

Subscribe to any query; deltas stream over Tauri events, FFI callbacks, or channels. Reactive UIs without polling.

Batches + transactions

Atomic batches and serializable snapshot-isolation transactions with conflict-aware commit validation.

Sync when you need it

Local-first always. Replication is opt-in, per deployment.

Mesh · LAN peers

mDNS + broadcast discovery, room-key isolation, WAL-delta replication across peers. No server on the network.

hakodb · net-sync

Cloud · central hub

Offline-first clients converge through a WebSocket hub: 5 ms micro-batched writes, room-scoped storage, group admission with API keys.

hakocloudserver

One engine, every stack

A flat C ABI (hakodb.h) under everything. Pick the SDK for your language — each lives in its own repo.
